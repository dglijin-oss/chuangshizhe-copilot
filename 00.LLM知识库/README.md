# LLM 知识库

> 来源：[karpathy 的 gist](https://gist.github.com/karpathy/)

一套基于 LLM（大语言模型）构建个人知识库的模式。

这是一个**思想文件**——设计用于复制到你自己的 LLM Agent（如 Claude Code、OpenAI Codex、OpenCode 等）中。它的目标是传达高层理念，你的 Agent 会与你协作，逐步构建出具体内容。

---

## 核心理念

大多数人与 LLM 和文档的交互方式是 **RAG（检索增强生成）**：你上传一批文件，LLM 在查询时检索相关片段，然后生成回答。这种方式能工作，但 LLM 每次都在从头发现知识——**没有积累**。问一个需要综合五份文档的深层问题，LLM 就得重新找到并拼凑相关片段。什么都没有沉淀下来。NotebookLM、ChatGPT 文件上传和大多数 RAG 系统都是这样工作的。

这里的理念完全不同。与其在查询时从原始文档中检索，LLM 会**增量式地构建并维护一个持久化的 Wiki**——一个结构化的、相互关联的 Markdown 文件集合，位于你和原始资料之间。当你添加新资料时，LLM 不只是为后续检索做索引——它会阅读资料、提取关键信息、并整合到现有 Wiki 中——更新实体页面、修订主题摘要、标注新数据与旧主张的矛盾之处、强化或挑战不断演化的综合分析。**知识被编译一次，然后保持最新**，而不是每次查询时重新推导。

这是关键区别：**Wiki 是一个持久的、不断复利的产物。** 交叉引用已经在那里了。矛盾之处已经被标记。综合分析已经反映了你读过的一切。每添加一份资料、每提出一个问题，Wiki 就变得更丰富。

你几乎从不亲自撰写 Wiki——**LLM 编写并维护所有内容**。你负责资料 sourcing、探索方向和提出正确的问题。LLM 承担所有脏活——总结、交叉引用、归档、记录，这些才是让知识库长期有用的工作。

> 实践中，我一边打开 LLM Agent，一边打开 Obsidian。LLM 根据我们的对话做编辑，我实时浏览结果——跟踪链接、查看图谱视图、阅读更新后的页面。
>
> **Obsidian 是 IDE；LLM 是程序员；Wiki 是代码库。**

## 应用场景

| 场景 | 说明 |
|------|------|
| **个人** | 跟踪自己的目标、健康、心理学、自我提升——归档日记、文章、播客笔记，构建关于自己的结构化认知 |
| **研究** | 对某个主题进行数周或数月的深入研究——阅读论文、文章、报告，逐步构建带演化论点的综合 Wiki |
| **读书** | 每读完一章就归档，为角色、主题、情节线建立页面及其关联。最终得到一个丰富的伴读 Wiki |
| **商业/团队** | 由 LLM 维护的内部 Wiki，输入来自 Slack 线程、会议纪要、项目文档、客户通话。Wiki 保持最新，因为 LLM 承担了团队没人想做的维护工作 |
| **其他** | 竞品分析、尽职调查、旅行规划、课程笔记、爱好深入研究——任何随时间积累知识且希望有条理的场景 |

## 架构

知识库分为三层：

### 1. 原始资料（`sources/`）
你收集的来源文档——文章、论文、图片、数据文件。**这些是不可变的**——LLM 只读不写。这是你的事实来源。

### 2. Wiki（`wiki/`）
LLM 生成的 Markdown 文件目录——摘要、实体页面、概念页面、比较分析、综述。LLM 全权负责这一层——创建页面、更新页面、维护交叉引用、保持一致性。**你阅读，LLM 编写。**

### 3. Schema（`CLAUDE.md` / `AGENTS.md`）
告诉 LLM Wiki 的结构、命名规范和操作流程的文档。这是核心配置文件——它让 LLM 成为**有纪律的 Wiki 维护者**，而不是通用聊天机器人。你与 LLM 共同演进这个文件，随着你对领域的深入理解。

---

## 操作流程

### 摄入（Ingest）
将新资料放入 `sources/`，告诉 LLM 处理它。流程：LLM 阅读资料 → 与你讨论要点 → 撰写摘要页面 → 更新索引 → 更新相关实体和概念页面 → 追加日志条目。一份资料可能涉及 10-15 个 Wiki 页面。

### 查询（Query）
向 Wiki 提问。LLM 搜索相关页面、阅读并综合回答，附带引用。**好的回答可以存回 Wiki 成为新页面。** 你要求的比较、分析、发现的关联——这些都是有价值的，不应消失在聊天记录中。

### 维护（Lint）
定期让 LLM 对 Wiki 做健康检查：页面间的矛盾、被新资料推翻的旧主张、无入链的孤立页面、有提及但缺页面的重要概念、缺失的交叉引用、可通过网络搜索填补的数据缺口。

## 索引与日志

两个特殊文件帮助导航 Wiki：

| 文件 | 用途 | 组织方式 |
|------|------|----------|
| `wiki/index.md` | 内容目录——每个页面的链接、一句话摘要、元数据 | 按类别组织（实体、概念、资料等） |
| `wiki/log.md` | 时间线记录——摄入、查询、维护的追加记录 | 按时间顺序，可被 `grep` 解析 |

## 可选工具

| 工具 | 用途 |
|------|------|
| **Obsidian Web Clipper** | 浏览器扩展，将网页文章转换为 Markdown |
| **qmd** | 本地 Markdown 搜索引擎，混合 BM25/向量搜索 + LLM 重排序 |
| **Marp** | 基于 Markdown 的幻灯片格式，可从 Wiki 内容生成演示文稿 |
| **Dataview** | Obsidian 插件，对页面 frontmatter 运行查询，生成动态表格 |
| **Git** | Wiki 就是 Markdown 文件的 Git 仓库——免费获得版本历史、分支和协作 |

## 为什么这能奏效

维护知识库的乏味部分不是阅读和思考——而是**簿记**。更新交叉引用、保持摘要最新、标注新数据与旧主张的矛盾、维持几十页的一致性。人类放弃 Wiki 是因为维护负担增长快于价值增长。**LLM 不会厌倦、不会忘记更新交叉引用、可以一次修改 15 个文件。** Wiki 保持维护状态，因为维护成本几乎为零。

> 人类的工作是：筛选资料、引导分析、提出好问题、思考一切意味着什么。
> LLM 的工作是：其他一切。

这个理念在精神上与 Vannevar Bush 的 Memex（1945）一脉相承——一个私人的、经过精心策划的知识库，文档之间有关联路径。Bush 没能解决的问题是：**谁来做维护？** LLM 解决了这个问题。

## 使用说明

本文档有意保持抽象——它描述的是理念，不是具体实现。确切的目录结构、页面格式、工具选择都取决于你的领域、偏好和 LLM 选择。以上所有内容都是**可选且模块化**的——挑有用的，忽略无用的。

正确的使用方式是：将此文件分享给你的 LLM Agent，一起协作实例化一个适合你需求的版本。
